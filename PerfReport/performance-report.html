Slice & Sell – Meta Quest 3 performance report

HCD-545 Assignment 2 · measured on a Quest 3 over USB, 27 Nov 2026 · Unity 6000.3.28f1, URP, OpenXR, Vulkan · every number below comes from a log, screenshot or profiler capture made that day

1 · Walkthrough (identical for every build)

Build: Development (no Autoconnect Profiler: an autoconnect player stops profiling once its 128 MB buffer fills, so the Profiler attaches over USB instead) · Display: 72 Hz (13.9 ms budget, the rate the app runs at) · Pose: standing · Input: Touch controllers · Level: 3 “Night Market” (unlocked in Development builds only) · the fruit thief appears on a fixed schedule in Development builds so every run does the same work.
  1. Launch from the headset Library; stand on the player spot; MENU sign → Recenter → Close. Shop sign → Level select → 3. Night Market.
  2. Warm-up ≈ 30 s: serve the first customer normally.
  3. FrameHud → Start route, then repeat for 3 min 30 s: read the order card up the street → take the fruit from its crate (left), put it on the board, cut along the guides (paring knife; Eto for watermelon) → lift the slices into the bowl by the board, add skewer / chilli if ordered → bowl on HAND OVER → turn the head to the left shophouses and to the right → ring the bell.
  4. At ≈1:45 an OVR Metrics overlay screenshot (Quest capture service over adb); at 3:30 stop and pull fps-log.csv / perf-log.csv and the compositor stats.
  5. Second short run (≈60 s of the same loop) with the Unity Profiler attached over USB; the last 2000 frames (27.8 s) of that run are analysed.
All builds are compared over the same first 3:00 of the route (build B’s route ended at 3:00). Average FPS and 1% low (FPS of the mean of the slowest 1% of frame times) are computed from the CSV rows of the route label and match the FrameHud.

3 · Optimisations (before → after)

1 · GPU: URP Intermediate Texture Always → Auto (HCD545-URP-Renderer.asset). “Always” renders each eye into an extra off-screen target and copies it to the swapchain. Evidence: GPU app time 7.31 → 7.11 ms = -0.20 ms (-2.7%); CPU work is not reduced (main 5.78 → 6.06 ms, render 4.06 → 4.18 ms) and FPS stays 72.0 in both, so the saving is GPU headroom only, and smaller than expected.

2 · Draw calls / shadows: stall decor batching + shadow trimming (BatchDecor, TrimShadows in StallBuilder). Without them every still crate wall, lantern and label is drawn on its own and casts a real-time shadow. Evidence (Rendering counters): draw calls 726 → 608 (-118 (-16.2%)), batches 552 → 432, shadow casters 217 → 113 (-104 (-48.1%)). The win is on the GPU, mostly the shadow pass: 7.57 → 7.11 ms (-0.46 ms (-6.1%)), and the 1% low rises 71.4 → 72.0 FPS (1 → 0 missed frames). Not the expected render-thread saving: SetPass calls go up 24 → 59, most likely because the combined meshes no longer draw through the SRP Batcher, and render-thread work rises 3.78 → 4.18 ms (+0.40 ms (+10.6%)); main thread 5.86 → 6.06 ms. Both threads stay far inside the 13.9 ms frame, so the GPU saving is the one that matters here; keeping the shadow trim but not combining the SRP-Batcher-compatible decor would be the next thing to test.

Not measured / limits: Unity’s GPU module (no data on Quest Vulkan; compositor App GPU time used instead); the Profiler analyses 2000 frames (27.8 s) of each 60 s run (the window’s frame history); Development builds only; one walkthrough per build.
